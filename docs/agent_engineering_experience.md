# RoxyPlan Agent Engineering 经验库

更新时间：2026-09-27

这份文档沉淀 RoxyPlan 在真实代码、日志、测试、ToolResult、持久化结果和用户验收中形成的 Agent Engineering 经验。它不是聊天记录汇编、功能说明书或当前状态快照。

当前能力与限制见 capability_boundaries.md；带日期的实现和验证状态见 current_status.md；项目事实、开发习惯与协作偏好见 project_workflow.md。

## 1 文档口径

### 1.1 证据等级

每条经验内部区分三类内容，不能只给整条经验贴一个笼统标签。

- 已验证事实：在对应时间和范围内，有代码、Git 输出、结构化日志、ToolResult、测试结果、真实持久化状态或桌面验收直接支持。
- 工程判断：由多项事实推导出的可复用结论，解释力较强，但没有在所有模型、入口和版本中验证。
- 当前推测：方向合理，但缺少完整实现、对照实验或当前运行证据。

“历史已验证”只证明当时的代码和场景。它不自动证明当前工作树仍保持相同行为。

### 1.2 进入经验库的门槛

普通 Bug 默认不进入经验库。至少满足下列一项，才建立经验候选：

- 找到执行链中的第一处偏差，并确认真实根因；
- 新证据推翻了原判断；
- 暴露出稳定的职责边界、状态生命周期或事实来源问题；
- 形成可迁移到其他 Agent 项目的测试、观测或安全方法；
- 明确了经验成立与不成立的边界；
- 同类问题重复出现，证明它不是一次性实现错误。

单个 formatter 缺失、一次点击坐标错误、临时 PATH 问题、重复 import 或一次 pytest 临时目录权限异常，应留在事故报告或运行说明中，不单独上升为架构经验。

### 1.3 合并和冲突处理

历史材料按以下顺序判定当前事实：

1. 当前代码、当前 Git 状态和当前可重复运行结果；
2. 带时间、入口、模型、命令、退出码和持久化结果的原始证据；
3. 原始事故总结；
4. 二次综合稿和回忆材料；
5. 没有验证的方案与推测。

同一事故被多份综合稿重复描述时，只生成一条经验，不按文档数量重复计权。新证据推翻旧结论时，不删除旧结论；在“认知修正”中记录旧判断、反证、替代结论和适用时间。

测试数字只有绑定日期、代码身份、命令范围、环境和完整终态时才有意义。不同日期、不同 lane 或不同工作树的数字不能相加，也不能画成自然增长曲线。

## 2 当前责任边界

以下内容已在 2026-09-24 的当前工作树中做过只读代码核对。

| 责任 | 当前权威 |
| --- | --- |
| 开放自然语言的结构化理解 | 一轮形成一份 canonical SemanticDecision |
| 结构归一化与校验 | SemanticPipeline 按 Normalize → Validate → Repair → Revalidate 处理 |
| 能力可见性和执行策略 | CapabilityRegistry |
| 工具参数、别名和 handler | ToolRegistry；执行策略字段从 CapabilityRegistry 同步 |
| 真实对象绑定 | BusinessResolver、ReferenceResolver、ReadSnapshot、SuggestionSnapshot |
| 执行与后置条件 | ToolExecutor、Service、Repository、ToolResult |
| 生产最终回复事实 | ResponseComposer 根据 ToolResult、受控流程 status 等已核验输入形成 ResponseOutcome；副作用成功仍必须有匹配的执行证据 |
| 客户端动作 | Agent 产生声明式 ClientAction，桌面 Dispatcher 执行并返回 ClientActionResult |
| 多轮临时状态 | InteractionStateCoordinator，按 conversation_id 隔离 |

当前 ActionClaimGuard 的代码注释明确说明：它不再是生产回复主路径，只保留给测试、诊断和旧兼容工具循环。旧资料中“继续给 ActionClaimGuard 加正则”的做法已被当前架构取代。

## 3 核心经验

### E01 沿完整执行链寻找第一处偏差

证据分层：已验证事实＝历史事故中的第一处偏差曾分别位于授权、状态、回复和评测层；工程判断＝沿完整执行链向前定位是可复用排障方法；当前推测＝无，任何新故障仍须重新取证。

来源：S01、S03、S06、S10、S14、C01、C04、C07。

#### 问题和最初判断

真实桌面中曾出现模型已经理解 add_plan，但请求仍进入澄清；也出现工具已经成功，最终回复却否认结果。表面上都容易被归因于“模型不稳定”。

#### 关键证据和第一处偏差

- 有的失败最早发生在授权层，不在 SemanticDecision。
- 有的失败最早发生在文案与 InteractionState 不同构的位置。
- 有的失败发生在 ToolResult 之后的回复组装。
- 有的失败来自测试记录器或比较器，而不是产品代码。

#### 根因和解决方式

只观察最终回复，会把下游症状误当成上游原因。排查固定沿以下链路推进：

~~~text
用户原句与前置状态
→ LocalFeatures / SemanticDecision
→ Normalize / Validate / Repair
→ ReferenceResolver / BusinessResolver
→ Authorization / Safety
→ ToolCall
→ ToolResult / Postcondition
→ Interaction before / after
→ FinalResponse
→ ClientAction / UI / 持久化
~~~

只修第一次从预期路径偏离的位置，并为这一层补可重复证据。

#### 为什么有效

后面的错误经常是前面偏差的连锁结果。修第一处偏差可以减少补丁、避免误改正常层，并让回归测试对应清晰责任。

#### 适用边界

如果中间阶段没有 request_id、结构化状态或结果日志，应先改善可观测性。缺证据时只能列出候选原因，不能武断宣布根因。

### E02 开放自然语言只能有一个最终语义裁决入口

证据分层：已验证事实＝历史上多个解释入口产生过冲突，当前代码已确认桌面和 Local Web 不构造旧 ModelToolCallLoop；工程判断＝开放自然语言应只有一个 canonical 语义裁决入口；当前推测＝其他新增入口是否遵守该约束需逐次核对。

来源：S02、S03、S04、S12、C01、C02、C03、C07。

#### 问题和最初判断

RoxyPlan 曾让 IntentRouter、SemanticActionParser、JSON fallback、旧 UI handler 和候选记忆规则依次解释同一句话。最初的修法是继续增加 Guard 和优先级。

#### 第一处偏差

第一次语义判断结束后，后续模块仍能重新解释整句并产生新工具。

#### 根因和解决方式

多个模块同时拥有意图最终裁决权。当前方向是：

- 极少数无歧义按钮、确认、取消或精确管理命令可走确定性入口；
- 其他自然语言只形成一份 canonical SemanticDecision；
- Normalize、Validator、Repair 和 Resolver 只能校正、校验、绑定、拒绝或澄清；
- 回复阶段不能重新开启第二个自然语言工具循环。

#### 为什么有效

任何工具调用都能追溯到同一份结构化决策，局部模块不会因为看到关键词而抢走方向盘。

#### 适用边界

统一语义入口不等于把所有权限交给模型。模型负责语义提案，程序仍负责授权、对象、风险、参数和执行。

### E03 模型提案、程序授权和工具执行必须分离

证据分层：已验证事实＝愿望误写入和 confidence 重复拦截均有历史故障证据，当前合同已拆分语义、策略和执行；工程判断＝模型提案、程序授权和工具执行应保持独立；当前推测＝不同风险动作所需的授权粒度仍要按能力验证。

来源：S04、S09、S12、S13、S14、S15、C01、C02。

#### 问题和最初判断

愿望、建议、假设和未来意向曾被直接映射成写工具；另一些请求已经通过结构校验，却被 confidence 阈值再次随机拦截。

#### 第一处偏差

语义分类、执行授权和概率置信度被当成同一件事。

#### 根因和解决方式

- SemanticDecision 描述用户可能想做什么；
- Policy 根据 request mode、polarity、modality、明确命令、风险、可逆性和字段完整度决定 execute、pending 或 no-action；
- ToolExecutor 只执行已注册并被允许的工具；
- confidence 只能提示不确定性，不能单独授予或撤销业务权限。

#### 为什么有效

系统既能保留自然语言覆盖，又能让副作用只由可解释、可测试的程序条件产生。

#### 适用边界

高风险和不可逆操作仍需明确确认。按钮或严格 DSL 已自带授权语义时，可以减少模型参与。

### E04 Normalize 必须早于 Validate，Repair 只能修结构

证据分层：已验证事实＝Normalize → Validate → Repair → Revalidate 的接线及特定 alias 回归已有代码和测试证据；工程判断＝Repair 应只修结构并保持业务不变量；当前推测／缺口＝当前边界检查尚不能证明字段不会被删除或非字符串业务值不会被改变。

来源：S02、S03、S04、S12、C02、C08。

#### 问题和最初判断

complete_plan 曾因为别名在进入 Normalizer 前被过滤而误报缺少 match_text。历史实现还曾无条件删除 unknown field，或让模型替用户选择非法 enum 的业务含义。

#### 第一处偏差

可修复信息在 normalization 前被永久丢弃，或 Repair 越权改变业务语义。

#### 根因和解决方式

正确顺序是：

~~~text
原始结构
→ tool/field/enum alias normalization
→ strict schema validation
→ 仅一次受限 structural repair
→ revalidation
~~~

设计合同要求程序化 Repair 只删除 ToolRegistry 明示的 safe-ignorable 字段并执行唯一确定的 alias 映射；模型 Repair 只处理白名单内结构错误，随后必须重新校验。两者都应保持 intent、tool 和已有业务值等不变量。当前实现已覆盖部分边界，但对字段删除和非字符串值变化的程序化不变量检查仍需补证，不能写成已经完全保证。

#### 为什么有效

结构错误可以恢复，但模型不能借 Repair 重新选择用户意图、目标或权限。

#### 适用边界

嵌套对象、数组和每个工具的 repair 合同仍需逐项测试。无法唯一修复时应澄清或拒绝。

### E05 ToolResult 和后置条件定义业务事实

证据分层：已验证事实＝项目出现过假成功和误报无数据，当前 contracts 与 ResponseComposer 已消费 ToolResult 及受控 status；工程判断＝副作用声明应绑定匹配的执行结果和必要后置条件；当前推测＝异步外部效果何时算完成取决于下一级回执合同。

来源：S01、S03、S04、S06、S09、S14、S15、C01、C04、C07、C08。

#### 问题和最初判断

系统多次出现“已经添加、保存、完成”，但真实数据没有变化；也出现读取成功却被回复层说成没有数据。提示词中要求“不要假成功”没有消除问题。

#### 第一处偏差

语言层把意图、措辞或无关日志当作外部状态证据。

#### 根因和解决方式

- 写入完成式声明必须有同一轮、同类操作的成功写 ToolResult；
- 关键写操作还要 read-back 或后置条件；
- 成功读取支持查询事实，但不能证明写入；
- 读取为空与系统失败分开；
- chat history 保存、memory retrieval 和 formal memory write 是不同事实；
- 工具或副作用成功必须由匹配的成功 ToolResult／后置条件证明；无 ToolResult 的确定性系统流程可以依据受控 status 得出流程成功，但不能借此宣称未经验证的副作用。

#### 为什么有效

最终回复和真实副作用共享同一个结构化事实源，不再由模型自证。

#### 适用边界

ToolResult 本身如果只表示“请求已接受”，还不能证明异步外部效果完成。此时需要下一级系统或客户端回执。

### E06 客户端动作需要独立的事实层和线程边界

证据分层：已验证事实＝Qt 跨线程事故有代码修复证据；工程判断＝客户端动作需要独立事实层和线程边界；当前推测／边界＝不同动作的真实视觉效果仍需逐项桌面验收。

来源：S04、S10、S14、C01、C07、C08。

#### 问题和最初判断

早期代码曾在工作线程直接操作 Qt 对象，也曾把“服务端产生动作请求”说成“桌宠已经完成动画”。

#### 第一处偏差

业务执行、Qt 主线程调度和用户可见效果被压成一个 success。

#### 根因和解决方式

LLM 和业务调用属于不确定耗时链，Qt 窗口、动画和 Timer 属于实时事件链。Agent 只产生 JSON-safe、可去重和可过期的声明式 ClientAction；桌面 Dispatcher 在主线程执行，ClientActionResult 再证明接受、拒绝或完成状态。

#### 为什么有效

模型延迟不会阻塞 UI，服务端也不会假装拥有本地客户端能力。

#### 适用边界

计划或记忆事务成功后，非关键动画失败通常不应回滚业务事务。视觉上是否达到用户预期仍需真实 UI 验收。

### E07 选择文案必须有同构的结构化状态

证据分层：已验证事实＝pending 与可见选择文案不同构造成过真实续接失败，当前工作树已有 offer/refinement/selection 类型化修改和相关测试；工程判断＝凡是邀请后续选择的文案都应有同构状态；当前推测／边界＝未完成真实桌面验收的分支不能视为最终闭环。

来源：S10、S12、S13、S14、S15、C01、C04、C07。

#### 问题和最初判断

助手曾说“要不要改记行动”“请选择第二项”，但没有保存对应 pending；用户下一轮回答“好”或“第二项”后，模型只能重新猜。

#### 第一处偏差

界面承诺了可继续操作，程序却没有同构的 interaction kind、能力、不可变参数和候选范围。

#### 根因和解决方式

任何邀请下一轮选择、补充或确认的文案，都要在同一轮建立可消费状态，至少包含：

- conversation_id、originating turn 和 TTL；
- capability 或 tool；
- 已知字段、缺失字段和 immutable arguments；
- 候选稳定 ID、展示顺序和允许输入；
- 成功、失败、取消、过期和澄清耗尽的终态。

2026-09-24 的未提交续接修改进一步把建议流程显式拆成 assistant_plan_offer、assistant_plan_refinement 和 assistant_plan_selection。细化阶段零工具、零写入，同一 offer 最多细化一次。

#### 为什么有效

控制流由结构化状态续接，不依赖模型回读上一句文案并重新生成参数。

#### 适用边界

明确的一轮命令不需要人为增加 pending。过期、跨会话或类型不兼容时应安全退出。

### E08 多轮指代必须绑定真实业务对象

证据分层：已验证事实＝部分计划选择链有真实桌面证据，当前 ReadSnapshot 与 SuggestionSnapshot 均保存稳定对象信息；工程判断＝多轮指代应绑定真实业务对象而不是实时下标；当前推测／边界＝跨会话或非结构化列表的通用指代仍需单独设计和验证。

来源：S06、S10、S11、S14、S15、C01、C04、C07、C08。

#### 问题和最初判断

“刚才那个”“第二项”“把它加入今天计划”曾被当成标题，或在列表变化后绑定到错误对象。把更多历史交给模型没有解决稳定对象问题。

#### 第一处偏差

指代词在解析来源和对象身份之前穿透到工具参数。

#### 根因和解决方式

- 模型识别引用关系；
- 程序限定当前 conversation 和来源轮次；
- ReadSnapshot 保存稳定 ID、展示顺序和标题等读取绑定；SuggestionSnapshot 另保存建议来源及 consumed 生命周期；
- 写入前重新读取真实对象并复核状态；
- 跨会话、过期、对象消失或数量不符时零写入。

#### 为什么有效

用户看到的“第二项”可以还原成不可变对象，而不是依赖实时下标或模型猜测。

#### 适用边界

普通聊天偶然出现的列表不能自动升级为可执行快照。原文边界不清时必须重新查询或澄清。

### E09 Command 和 Payload 必须隔离

证据分层：已验证事实＝载荷正文被再次当作命令的误触及其回归已有证据；工程判断＝命令区与业务载荷应先隔离再路由；当前推测／边界＝这不能扩张成第二套开放中文语义系统。

来源：S06、C01、C02、C07、C08。

#### 问题和最初判断

“记住：我喜欢你跳舞”中的“跳舞”、记忆检索正文中的“删除”或“完成”曾再次触发动作扫描。最初通过调整 if 顺序和加关键词止血。

#### 第一处偏差

业务正文和检索内容被当成控制指令重新扫描。

#### 根因和解决方式

先识别 command region、polarity 和 protected payload，再让命令区参与确定性路由。载荷原样进入参数并由 Resolver 校验，不能回流到动作选择。

#### 为什么有效

用户保存或讨论一个动作词，不会等同于要求立即执行该动作。

#### 适用边界

这条规则适合精确命令和载荷保护，不应扩张成新的大型本地中文语义系统。开放式语义仍由唯一 SemanticDecision 处理。

### E10 复合写操作需要 Batch Admission

证据分层：已验证事实＝历史复合请求出现过静默丢项和错误 partial commit；工程判断＝含写入的复合请求需要整批 admission 和逐项 ToolResult；当前推测／边界＝具体批量上限和允许的组合仍受产品能力与来源可信度限制。

来源：S06、S14、C02、C05、C07、C08。

#### 问题和最初判断

复合请求曾静默丢掉第二项，或先执行错误第一项再询问剩余内容。关闭 ActionBatch 或把 max_steps 设为 1 看似更安全。

#### 第一处偏差

执行器之前没有判断整批语义是否完整、一致且获授权。

#### 根因和解决方式

每个 clause 保留解析状态、依赖和对象。只要包含写入且任一项缺字段、引用不明、需确认或越界，默认整批零写入并澄清。完全明确且低风险的批量操作才进入执行，每个 ToolResult 独立保留。

#### 为什么有效

系统不会通过“少做一点”掩盖错误目标或意外 partial commit。

#### 适用边界

多个纯查询可以聚合。已展示、结构校验并带稳定 ID 的可信快照，与模型临时自由生成的多动作应采用不同上限。

### E11 Memory 是多种生命周期，不是一个功能名

证据分层：已验证事实＝正式记忆、候选兼容、聊天历史和回复引用混淆均有项目证据；工程判断＝不同来源与生命周期必须分开建模；当前推测／边界＝保存策略属于产品选择，当前合同以 capability_boundaries.md 为准。

来源：S04、S06、S13、S14、S15、C02、C06、C07、C08。

#### 问题和最初判断

聊天消息保存、候选记忆、正式记忆、摘要、冲突和归档曾被混称为“记住了”。显式保存还曾被候选流程抢占。

#### 第一处偏差

来源、审核状态、持久化正文和用户可见事实没有分开建模。

#### 根因和解决方式

- chat history 只证明消息被保存；
- retrieval 只证明读取了既有事实；
- candidate 是内部治理对象，不等于正式记忆；
- formal memory 必须由 canonical 工具和成功 ToolResult 建立；
- archive、conflict、summary 和 working state 各有独立生命周期；
- previous assistant message 可以是合法引用来源，但持久化正文必须再做受限事实提取并验证来自 source，不能默认保存整段回复。

#### 为什么有效

系统可以准确说明“保存了什么、来自哪里、处于什么状态”，也避免把角色生成文本当成用户事实。

#### 适用边界

普通稳定信息是否直接保存、先确认或完全不保存是产品策略，不是通用技术定理。候选记忆已经退出当前用户交互，但兼容结构仍可能保留。

### E12 Context Engineering 需要来源、预算和生命周期

证据分层：已验证事实＝ContextBuilder 已分 section，当前诊断记录 name、source、characters、item_count 和 trimmed；工程判断＝上下文还应显式管理来源、预算和生命周期；当前推测／缺口＝时间、敏感性、入选原因等更丰富元数据及完整 RAG 召回质量尚未实现并统一验证。

来源：S06、S14、C01、C02、C03、C05、C07、C08。

#### 问题和最初判断

把更多历史、记忆和知识全部塞给模型，曾被视为解决连续性和指代的直接方法。

#### 第一处偏差

短期操作状态、长期事实、旧摘要和检索知识被当成同一种上下文。

#### 根因和解决方式

- 人格核心、能力边界和真实性约束稳定注入；
- 正式记忆、计划、目标和相关摘要按任务选取；
- 当前 conversation 的 pending、序号和 preview 不跨窗口继承；
- 当前每个 section 已记录名称、来源、字符数、条目数和是否裁剪；后续若要审计隐私与时效，再扩展时间、敏感性和入选原因等元数据；
- 知识检索只能提供回答证据，不能授权写工具或覆盖 ToolResult。

#### 为什么有效

减少无关信息、隐私暴露和状态污染，同时保留可解释的连续性。

#### 适用边界

字符预算不是固定常数，需要结合模型窗口、任务类型、召回质量和线上评测调整。完整 RAG 方案仍是待验证设计。

### E13 事实骨架与人格表达必须分层

证据分层：已验证事实＝回复假成功、事实遗漏和记忆 dump 体验均有历史证据；工程判断＝事实骨架与人格表达应分层；当前推测／边界＝不同模型下最合适的表达约束仍需真实用户验收。

来源：S01、S04、S14、C01、C05、C07、C08。

#### 问题和最初判断

完全让模型自由表达会产生假成功；直接打印 ToolResult 又会让角色退化成数据库接口。

#### 第一处偏差

事实正确性和表达自然度被迫由同一层同时负责。

#### 根因和解决方式

程序先固定操作类型、成功失败、对象、数量、日期和错误原因；模型或 ResponseComposer 只在该事实骨架内组织语气、详略和人格。任何润色都不能改变事实。

#### 为什么有效

回复既能保持角色感，也不会改写系统状态。

#### 适用边界

主观建议和情感陪伴没有 ToolResult 事实骨架，但仍不能伪造外部动作、记忆或用户信息。

### E14 测试必须隔离私人数据和共享工作树

证据分层：已验证事实＝历史测试污染正式数据及当前 Git/ignore 状态均有证据；工程判断＝测试必须使用仓库外隔离根并做前后指纹核对；当前推测／边界＝权限残留和平台差异仍需按环境处理。

来源：S02、S05、S06、S09、S14、S15、C02、C04、C07、C08。

#### 问题和最初判断

测试曾只替换 memory_file，却让 backup、audit、lock 或其他路径落到真实 data/private。另一次清理把既有 pet_config 差异误当成当前任务产生并还原。

#### 第一处偏差

系统没有完整 data root 注入，也没有先记录工作树所有权。

#### 根因和解决方式

- 测试注入完整临时 Repository / data root；
- basetemp 位于仓库外并禁用缓存；
- 对正式私人路径做写入防火墙、前后清单和哈希校验；
- 修改前刷新 branch、HEAD、staged、tracked 和 untracked；
- 既有差异默认属于用户，只精确暂存本轮文件；
- memory.json 和 data/private 与代码、example 数据分离。

#### 为什么有效

“测试通过”同时意味着程序合同通过且真实用户状态未被污染。

#### 适用边界

只有用户明确授权丢弃，并且目标已精确核对时，才能还原、移动或删除既有资产。

### E15 自动化、在线模型和真实 UI 是不同证据层

证据分层：已验证事实＝单元、在线模型、日志和真实 UI 之间出现过相互不等价的反例；工程判断＝这些应作为独立证据层报告；当前推测／边界＝没有任一单层能够替代所有其他层。

来源：S01、S02、S03、S07、S08、S10、S11、S13、S15、C01、C03、C04、C07、C08。

#### 问题和最初判断

Stub、模块测试或生产组合根回放通过后，真实 provider 仍可能返回空候选；在线工具链通过后，Qt 线程、入口、窗口和动画仍可能失败。

#### 第一处偏差

报告使用“已验证”却没有说明验证入口和未覆盖层。

#### 根因和解决方式

验证结果分开报告：

1. 静态检查和编译；
2. 聚焦单元与事故回归；
3. production / compatibility / historical 合同；
4. 生产 composition root 回放；
5. 真实在线 provider；
6. 真实桌面入口、UI 和持久化后置条件。

用户只要求某一层时可以停在该层，但必须明确其他层未执行。真实桌面验收应从 roxy.bat、桌宠双击和“打开聊天”的实际入口开始；复用已有聊天窗口不能证明入口。

#### 为什么有效

局部通过不会被提升成端到端成功，失败也能归到正确层级。

#### 适用边界

不是每次文档或低风险代码修改都需要完整桌面验收。验证深度应与风险和用户授权匹配。

### E16 非确定性评测和 Evaluator 也需要工程合同

证据分层：已验证事实＝S07、S08 记录了盲测角色污染、统计口径和评测器事故；工程判断＝Evaluator、数据冻结和统计规则本身也需要工程合同；当前推测／边界＝跨模型的泛化结论需新的独立评测确认。

来源：S03、S07、S08。

#### 问题和最初判断

45/45 曾被当成严格封闭盲测；pass@3 曾被误读成三次都通过；runner schema 和比较器错误也污染过产品结论。

#### 第一处偏差

评测角色、数据隔离、指标定义和报告 schema 没有冻结。

#### 根因和解决方式

- 生成、开发和评测角色隔离；
- 评测集、candidate Git 身份和 runner hash 绑定；
- 同时报告 pass@1、pass@k、all-k-pass、all-k-fail 和 flaky；
- 保存逐次原始输出；
- evaluator 失败与产品失败分开；
- evaluator 修复后建立新 run，不覆盖失败证据；
- aggregate 与 per-case 必须相互校验。

#### 为什么有效

它能暴露“至少一次成功，但仍有危险误写”的不稳定系统，也避免错误评测器驱动产品修复。

#### 适用边界

完全确定性的纯程序模块不需要重复采样，但其评测脚本仍要验证数据集合和统计口径。

### E17 删除重复职责通常比继续加 Guard 更可靠

证据分层：已验证事实＝多个语义入口、重复白名单和重复事实裁判曾引发真实事故；工程判断＝单一 owner 并删除重复职责通常比继续叠 Guard 更可靠；当前推测／边界＝每次删除仍需先核对兼容面与回滚需求。

来源：S01、S02、S03、S04、S12、S14、C01、C02、C05、C07、C08。

#### 问题和最初判断

每次误触都增加一个正则、Guard、fallback 或优先级，单项看都合理，组合后却让多个模块拥有相同裁决权。

#### 第一处偏差

同一事实、意图或状态被多份实现重复维护。

#### 根因和解决方式

发现系统不断增加旁路时，先列出谁拥有：

- 自然语言裁决权；
- schema 和 alias；
- 能力可见性与风险策略；
- 真实对象绑定；
- 执行事实；
- pending 生命周期；
- 最终回复事实。

每项只保留一个 owner，其他模块消费结果或做窄校验。删除失效的第二入口比继续为两套逻辑补同步更可靠。

#### 为什么有效

减少顺序依赖、状态漂移和指数增长的测试组合。

#### 适用边界

删除前必须确认兼容面和回滚需求。保留兼容 API 不等于保留第二套自然语言裁决。

## 4 历史认知修正

| 旧判断 | 新证据 | 当前结论 |
| --- | --- | --- |
| 45/45 是严格封闭盲测 | 生成、开发和首次评测没有完整角色隔离 | 该结果降级为冻结补集；独立 blind 另行记录 |
| SemanticPipeline 存在就代表生产在使用 | 历史搜索发现 validate_decision 当时没有调用 | 组件存在和生产必经是两件事；当前已重新核对接线 |
| unknown field 可以自动删除 | repeat、date、duration 等可能承载业务语义 | 只删除 Registry 明示的 safe-ignorable 字段 |
| invalid enum 可以交给模型猜 | 模型会改变业务含义 | 只允许唯一确定的 enum alias，否则澄清 |
| Prompt 写“不改变 intent/tool”就够 | Prompt 不能提供程序不变量 | Repair 后程序化比较不变量 |
| 给 ClaimGuard 加更多正则就能防假成功 | 正则曾误伤真实只读结果，并形成第二事实裁判 | 当前生产事实出口由 ResponseComposer 和 ResponseOutcome 负责 |
| 分批 passed 数相加就是全量通过 | 集合重叠、运行中断和范围不同 | 必须提供完整 collection 或去重清单与完整终态 |
| pending 后最终写对了就证明状态正确 | 历史链曾先取消 pending，再重新问模型 | 必须断言原 pending 被直接创建、消费和收口 |
| 给指代补几个同义词即可 | 新同义表达继续失败 | 引用来源、业务对象和操作目的地分开建模 |
| Stub 输出规范，所以在线候选可靠 | 真实模型可能返回空或不可解析结构 | 降级只能从已定位原文做受约束提取 |
| 建议后禁止继续追问 | 短答仍需要合法的条件补充入口 | 用 offer → refinement → selection 表达一次可选细化 |
| 所有批量新增统一最多三项 | 已展示快照和自由生成动作的可信度不同 | 安全上限按来源可信度分层 |
| 当前没观察到，所以历史中不存在 | 用户在旧会话中找到了对应内容 | 未观察到不等于不存在；先说明证据范围 |
| 找到现成聊天窗等于桌面入口通过 | 没有验证桌宠启动和打开聊天动作 | 入口验收必须走真实用户路径 |

| V2.2 代表产品版本已到 V2.2 | AGENTS 和 current_status 明确区分 | 产品仍为 V0.9，V2.2 是稳定化工作流 |

## 5 尚未升级为已验证经验的方向

### RAG

当前可复用判断是“检索提供受控知识证据，不能授权业务写入”。完整向量入库、召回质量、引用正确率、删除、重建和用户隔离仍缺统一生产证据，不写成已经实现。

### 云端迁移

当前判断是先冻结 JSON-safe 合同、Repository、幂等和客户端能力边界，再迁移入口与存储。公网部署、云数据库、账号和跨设备同步未因此获得实现授权。

### 自适应成长与竞赛算法

Learner State、Policy、Intervention、Verifier 和 Evaluation Harness 是设计方向。没有连续数据、Baseline、消融和真实用户结果时，不宣称 RL、自适应策略或算法创新已经成立。

### 时间与时区

早期材料记载时区错误曾影响舞蹈动作，但没有恢复出精确代码路径。可以保留工程判断：一旦“今天、现在、几点、TTL、定时任务”参与业务条件，timezone 就是业务语义；该历史事件的具体根因仍属待验证。

## 附录 B 维护约束

- 不把历史测试数字写成今天刚运行。
- 不把评审建议、RAG 方案或云端规划写成已经实现。
- 不把用户说“差不多可以”升级成完整工程闭环。
- 不把多份二次综合稿当成多次独立验证。
- 不把 Git 分支名、产品阶段和工程里程碑混为一谈。
- 不为增加篇幅把每个小 Bug 抽象成架构哲学。
- 新证据推翻旧结论时，新增修正记录并更新条目状态，不静默删除历史。

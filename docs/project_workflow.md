# RoxyPlan 项目工作流程

更新时间：2026-10-13
适用范围：本仓库的长期维护、故障修复、文档同步与当前稳定化协作。

这是 RoxyPlan 可公开审阅的项目工作说明。它不保存个人协作偏好、本机绝对路径、用户昵称、身份暗号、私人对话、密钥、凭据或正式数据正文。个人协作偏好和本机信息只放在被 Git 忽略的 `docs/local/project_preferences.local.md`；产品中的个人事实仍按能力契约和用户明确授权保存，不写入项目文档，也不因为本文件的存在自动写入 `memory.json`。

可复用的 Agent Engineering 经验单独维护在 [agent_engineering_experience.md](agent_engineering_experience.md)。本文只保留稳定项目事实、通用工作顺序、安全边界和验证流程，避免“当前规则”和“历史经验”重复维护。

## 0. 稳定项目档案

- 项目名称：RoxyPlan，中文名“洛琪希计划”。
- 产品定位：长期成长陪伴 AI 桌宠。
- 当前产品阶段：V0.9 Windows 本地原型。V2.1、V2.2 是语义可靠性和稳定化工作流名称，不等于产品版本，也不证明 Git 中存在同名分支。
- 正式项目根以当前 Git 仓库根目录为准。根目录名称保持稳定，不用版本号、平台或实验名重命名。
- 主要入口：PySide6 桌宠与聊天窗口；经批准的 Local Web 只在 `server/` 作为现有核心的适配层。
- 共享核心：桌面端和 Local Web 复用 ConversationService、Agent、Tool、Memory、Growth 和 Repository，不维护第二套业务大脑。
- 私人数据：正式长期记忆位于 `memory.json`，聊天、计划、行动、成长等私人数据位于 `data/private/`，桌宠设置位于 `data/pet_config.json`。测试不得默认读写这些路径。
- 版本事实：Git 分支、HEAD、dirty worktree、已存在分支和提交只能由当次 Git 输出证明。聊天中讨论过 Stable、比赛、Cloud 或 Web 规划，不等于这些分支已经创建。
- 状态事实：能力合同看 `capability_boundaries.md`，日期化实现和测试看 `current_status.md`，当前代码优先于旧交接。

## 1. 阅读入口与权威分工

接手顺序：完整读取 [AGENTS.md](../AGENTS.md)，然后读取 [capability_boundaries.md](capability_boundaries.md)、本文、[current_status.md](current_status.md) 及任务直接涉及的专题文档。如果本机存在 `docs/local/project_preferences.local.md`，再把它作为本机偏好补充读取，但它不能覆盖项目硬边界和当前能力契约。处理 Agent 架构、可靠性、状态、Tool、Memory、Context 或测试方法时，再按需读取 [Agent Engineering 经验库](agent_engineering_experience.md)。历史交接用于理解责任链与过去证据，不作为当天状态证明。

- `AGENTS.md`：硬限制、目录边界与新任务入口。
- `capability_boundaries.md`：产品能力、推荐自然表达、确认与失败契约。
- 本文：稳定项目事实、通用工作顺序、安全边界和验证流程。
- `agent_engineering_experience.md`：经过来源去重和证据分层的长期经验、认知修正与复盘模板；不保存最新测试数字。
- `current_status.md`：带日期的完成度、故障处置、测试证据与未执行项。
- [CapabilityRegistry](../modules/capability_registry.py)：当前执行策略与模型可见性；[ToolRegistry](../modules/tool_registry.py)：工具参数、别名和 handler。不要在文档再造 schema／白名单。

用户新决定只在明确的任务和授权范围内更新约定；“继续”不扩张权限，“暂停”停止当前推进。发现文档、代码或旧决定冲突时，先核实日期、范围和实际路径，记录差距，不凭某条旧经验覆盖最新明确决定。只有用户明确要求才更新 Codex 全局协作记忆；维护仓库文档不等于获得修改全局记忆的权限。

后续项目工作默认承担功能审计职责：对照当前代码、实际运行结果、已承诺能力与用户期望的效果，指出有证据的差距，并区分已支持功能的缺陷、尚未设计的能力和体验改进建议。提出方案时同时评估用户收益、开发与验证成本、现有架构可复用的优势及其限制，优先给出当前阶段可落地的最小方案；未经验证的效果和根因明确标为待验证，不把理想体验直接当成实现承诺。

## 2. 本机偏好覆盖层

个人协作习惯、本机路径和本地资产保留策略不进入公开仓库。它们统一维护在被 Git 忽略的 `docs/local/project_preferences.local.md`。新 Agent 在该文件存在时按需读取；文件不存在时，完全依照 `AGENTS.md` 和本文工作。该本地文件只能补充偏好，不能降低安全限制、扩大授权或改变当前产品契约。

## 3. 任务分诊：修程序还是规范表达

| 现象 | 分类与动作 | 不应采用的方式 |
| --- | --- | --- |
| 明确支持的完整请求执行错误，误写、假成功、确认循环 | 核心缺陷：保存故障链，补回归，修第一处偏离 | 把责任归给用户，或偷偷改为不支持 |
| 已承诺的序号／刚展示集合／后续续加失败 | 已支持快捷能力缺陷：保留操作类型、稳定对象和集合 | 每次要求用户重说标题作为永久替代 |
| 省略对象、混合意图、指代不明、过期引用 | 模糊输入：有界澄清；仍不明就给完整推荐句并退出 | 猜目标执行或无限增加特殊分支 |
| 关闭的复杂操作、危险批量删除或原本未设计功能 | 说明限制，只指向真实可用替代入口 | 假装能做并创建纯文本确认循环 |
| 当前模型表达流畅但无法确定执行事实 | 检查 ToolResult 与真实后置条件，必要时保守回复 | 用提示词或“看起来合理”代替事实核验 |

用户层约定提高效率，但程序安全底线不能外包给用户。是否“刻意为难”不影响零误写、零假成功和有界退出要求。已支持但失败的功能是已知缺陷；用户暂缓的确认需求是暂缓，不改称未设计。

## 4. 修改前的安全基线

### 多员工基线同步（2026-10-12 用户确认）

总控制台负责成果集成及相关员工的开发基线同步。工作树不会自动获得主目录的新改动；主目录整合完成也不代表员工已经同步。派发依赖新成果的任务前，总控应核对相关员工的实际代码和未提交修改，完成或明确协调必要同步后再开始开发，不仅在提示词中要求员工自行寻找最新版本。

- 已完成批次默认用明确 Commit 交接。总控审查、集成并完成相应验证后，公布集成 Commit，由员工在安全的任务边界同步；运行中的任务不强行切基线。尚未收口或仍含未提交集成成果时，限定文件清单、补丁与哈希快照仍可作过渡，不能把旧 HEAD 当作完整运行基线。
- 相同文件跳过；员工已有独有修改必须保留，双方修改重叠时先比较合并，不用整体覆盖、reset 或 clean。若同步涉及运行中的开发任务，先协调该任务停止修改相关文件。
- 同步只覆盖本任务所需代码、运行资源、测试和协作约定，不复制正式用户数据、私人配置、密钥、虚拟环境或测试运行产物。
- 同步后核对关键差异与入口，明确哪些员工已同步、哪些尚未同步；下一次集成后继续承担这一职责。同步不授权覆盖员工改动、提交未收口成果或推送。

### 完成批次默认提交（2026-10-13 用户确认）

- 已获授权的开发、修复或文档任务完成并按本批范围验证后，默认在自己的岗位分支创建一次本地 Commit，无需逐次再申请提交许可。总控完成一个集成批次后同样提交一次。用户要求暂不提交时，以当次要求为准；只读任务没有改动时不创建空提交。
- 开工时记录既有 dirty 状态及任务文件范围。提交前审查 diff，使用明确文件清单；同一文件混有以前批次或他人成果时，只暂存本批相关 hunks，不把整个 dirty worktree 当作本批交付。无法可靠区分时，保留成果并报告具体阻碍，不强行提交。
- 当前存量未提交成果仍需单独审查收口；默认提交约定不等于立即把所有旧 UI、资源或其他员工成果一起提交。任务需要依赖未提交基线时，交付中同时注明基线快照及来源，直到总控完成基线收口。
- 不提交正式用户数据、私有配置、凭据、虚拟环境、构建目录、临时测试产物及员工不负责的文件，不使用 `git add .`。已有他人暂存内容保持原样，不擅自清空索引；发现混合暂存时停止提交并报告。
- 提交前完成必要的针对性验证和 `git diff --check`，检查最终暂存 diff；无需为纯文档修改跑业务测试。交付统一报告修改结果、实际验证证据、遗留问题和 Commit ID。Commit 只说明代码版本，不代表真实模型、桌面或用户验收已通过。
- 先固定本批文件职责与跨员工接口。总控审查员工 Commit 后集成，避免再以整树复制作为常规交接。冲突先比较双方成果，禁止 reset、clean 或覆盖未提交工作来换取同步成功。
- 普通静态检查及少量离线检查可自行执行；Qt 套件、构建、全量回归和大量在线调用依照总控安排串行执行，Windows 桌面继续遵守独占规则。已安排的时段不因提交规则变化而撤销。
- 默认提交不包含推送、发布 Release、分发 APP 或清理工作树的授权，这些操作仍需单独授权。

### 修改前检查

1. 刷新当前分支、HEAD、tracked／untracked／staged 状态及任务文件 diff；不把旧快照数字当成当前状态。
2. 保存精确补丁与文件清单，按范围保留未跟踪的运行依赖、测试和文档；补丁不是发布包，正式数据和已有配置变更不能未经核对打包。
3. 明确本轮编辑文件、禁止触碰文件与验证计划。存在并行 agent 时先分配不重叠的文件范围，所有工作共享目录，不能互相回滚。
4. 用 `rg` 优先查指定模块、关键字段和调用点；本地编辑用 `apply_patch`。避免 broad reset、checkout、clean、递归删除或批量格式化。
5. 不使用 `git add .`。完成后按上方批次规则暂存并提交一次；推送和清理仍须单独明确授权。

目录整理也遵守同一原则：先做只读资产地图，确认 Git、worktree、引用、独有内容和备份价值；再给出精确清单，由用户单独确认移动或删除。测试目录“看起来没用”不是删除证据，历史压缩包“看起来像备份”也不等于它是可恢复的真实备份。

不修改 `modules/llm_client.py`、`memory.json`、私人配置或正式用户数据，除非用户明确指定该文件及变更目的。保持桌宠、聊天、设置和本地数据兼容。FastAPI 只可在已批准的 `server/` 适配范围；不新增数据库、语音、复杂解析、公网或云端集成。

2026-09-21 用户明确纠正：RoxyPlan 正式运行时使用现有 DeepSeek provider，不是 OpenAI API。不切换到 `aivalux`，不新增 Provider，也不为验收改写私人配置。需要真实模型验收时，通过生产 `RoutedLLMClient` 和专用隔离 acceptance root 调用该 DeepSeek 路径；新的验收根统一放在 `test_workspace/runs/<run-id>/`，报告必须同时核对 provider 元数据、语义决策、ToolResult、开发日志和隔离数据。Codex 自身所用模型与 RoxyPlan provider 是不同对象。

## 5. 故障定位与最小修复流程

推荐责任链：当前用户句与上下文 → 结构化语义 → schema／实体校正 → 真实对象解析 → 能力可见性与授权 → typed interaction／确认 → 执行 → ToolResult／后置条件 → 最终回复。

1. 保存最小完整多轮链，列出预期、实际、数据变化及首次偏离。记录时间与来源，诊断没有开启时不编造模型原始输出。
2. 先建立失败回归，包括工具次数、目标稳定 ID、确认前零写入、真实数据和最终状态，而不只测某句文案。
3. 修职责边界：模型负责理解目的；本地负责精确命令、安全限制、否定、当前句明确实体、真实对象和结果核验。普通聊天不能被业务词命中强行升级为写操作。
4. 一次只做一个可解释的小改动，沿既有语义链接入，不新增平行路由。必要的职责提取逐步实施；复杂清理、旧兼容处理器删除留到用户批准的后续阶段。
5. 增加同类反例与非业务反例，再验证核心闭环和相关模块。回复层的修复要同时测误拦截与漏拦截，不能只扩大成功词列表。
6. 完成后同步状态和必要专题，准确写已修、剩余问题、暂缓与未执行项。没有证据就不提前宣布封版。

### 真实故障闭环：从用户原句追到最终数据

只测解析器、工具执行器或构造好的下游状态，不能证明真实自然语言链路已经修好。处理同类故障按以下顺序推进：

1. 先读取最新正式聊天与对应开发日志，按时间、会话和 trace 对齐用户原句、模型输出、语义状态、工具结果与最终数据；同时区分核心支持表达、故意为难的边界探测和原本未设计的功能。
2. 找到链条中的第一处偏离，而不是只修改最终回复。表面相同的“模型不稳定”可能分别来自模型输出、本地解析、授权、状态、工具执行或回复组装；必须按本次证据归因。历史实例和认知修正统一见经验库。
3. 先补可重复的聚焦契约，覆盖工具次数、参数、确认前零写入、稳定对象和后置数据，再做最小代码修复。离线回归用于锁定本地责任，不代替真实模型验收。
4. 真实语义故障必须再通过生产组合根调用现有 DeepSeek provider；使用 `test_workspace/runs/<run-id>/` 下的全新隔离数据根，不替换 provider、不改私人配置、不预置快照冒充完整链路。验收报告保留真实 provider／model 元数据，证明不是 Stub、Fake 或另一个供应商。
5. 对“同义句偶发成功／失败”至少准备三组等价自然表达，并将每组重复三次。每次都核对用户可见回复、`SemanticDecision`／交互状态、每个 `ToolResult`、开发日志和隔离后的最终 JSON；任一层不一致都继续定位，不能因为某一次成功或测试变绿就宣布修复。
6. 在线验收暴露新的上游偏离时，回到第 1 步补证据与聚焦契约，不把它解释成无法处理的模型随机性，也不继续堆叠某一句中文的正则。

像素级桌面操作只为验证桌宠入口、窗口、焦点、显示、动画和客户端回报等 UI 问题。若当轮原生 Windows 控制不可用，而用户允许验证非视觉链路，可以使用 `ChatWindow` 的生产组合根完成“真实 DeepSeek → 语义 → 工具 → 日志 → 隔离持久化”验收；必须明确报告没有验证鼠标入口和视觉表现，不能把它写成完整桌面验收。

## 6. 经验库使用方式

长期经验统一维护在 [agent_engineering_experience.md](agent_engineering_experience.md)，本文不再复制一份经验表。处理真实故障时先按本文第 5 节完成现场闭环，再判断是否达到经验库门槛。

进入经验库的条目必须写清：最初判断、真实现象、关键证据、第一处偏差、根因、解决方式、为什么有效、适用边界、来源编号和后续修正。普通执行记录、临时测试数字和某一句中文的特判不进入长期条目。

经验库提供方法，不替代当前状态。遇到冲突时，优先核对当前代码、当前能力合同和带日期的运行证据；旧经验应标记为被修正，而不是强行套用。

## 7. 验证与证据报告

- 自动化默认通过 `scripts/run_isolated_tests.ps1` 启动。脚本为每次运行建立唯一的 `test_workspace/runs/<run-id>/`，并把 pytest `basetemp`、系统临时文件、JUnit、完整输出、退出码和其他运行产物收拢到该目录；同时使用完整隔离数据根、正式路径防火墙并禁用 pytest cache，不读写、恢复、清空或模板覆盖正式计划／记忆。
- 手动跨天模拟使用 `scripts/run_simulated_days.ps1` 和仓库外全新隔离根；脚本记录正式路径运行前后指纹到该根，发现变化保留证据并报告，不自行归因或回滚。它不修改系统时间，也不沿用正式记忆、聊天或设置；模型凭据只通过现有环境变量或该隔离根的凭据存储使用。
- `test_workspace/runs/` 全部由 Git 忽略。成功运行默认删除本次目录；失败运行保留现场供诊断，确认无用后只精确删除对应 run。不得在仓库根目录重新创建 `.codex_pytest_*`、散落的 test run、评测副本或测试压缩包。
- 按风险先运行新增故障聚焦与核心学习闭环，再运行 `production_contract`、`compatibility_contract`；`historical_baseline` 单独执行和报告。编译及原生 `git diff --check` 是独立检查。
- 三条 lane 的含义与命令以 [tests/README.md](../tests/README.md) 为准。历史冻结失败不混为生产失败，也不能靠改分类、删断言或跳过事故模块“跑绿”。
- 报告包含运行日期、代码阶段、选择器、通过／失败／中断数和报告路径。旧结果引用必须带日期；聚焦通过不等于全量通过。失败后复跑通过也保留首次证据，未确认的环境原因不武断归因。
- 隔离 Stub/Fake／结构化夹具只证明本地契约，不证明真实模型中文体验。在线、UI、unfiltered 未运行就分别写“未执行”，不推断为通过。
- 真实模型报告至少包含 provider／model 元数据、逐轮原句与回复、语义决策、工具调用及结果、开发日志位置和最终隔离数据。没有这些对应关系，只能算局部验证。
- 对已出现随机性的同类自然表达，采用多组等价句并各重复至少三次；任何一次错误写入、漏写、假成功或状态串线都算该链未通过。
- 原生行尾警告不等于空白缺陷；使用仓库现有 Git 行尾设置核查，不改设置或大范围格式化已有用户文件。

测试数和最新运行路径只在 `current_status.md` 维护，本文不复制一份容易过期的“最新全绿”。

## 8. 用户明确要求桌面验收时

先使用当轮可用的 computer-use 技能和工具，刷新 UI 状态。保留真实入口：从项目根启动 `roxy.bat`，小桌宠双击两下，再选择“打开聊天”。只找到已有聊天窗口，不等于验证入口。

新建空白会话，编写新的自然多轮表达，等待真实模型返回，同时检查界面、日志与实际结果；不要只照抄旧样例。用户授权的真实验收记录属于用户数据，保留失败证据，不擅自删除。工具无法稳定操作桌宠时说明限制，不把自动显示聊天窗口写成等价入口验收。没有用户本轮明确要求时不启动或操控桌面。

## 9. 维护触发与收口

用户新增或撤销协作规则、临时许可、验收分工，以及测试隔离或证据流程变化时，小范围更新本文和必要入口。能力范围变化更新能力边界，测试结果和单次事故事实更新当前状态；同类故障揭示出的可复用原则合并进唯一的 Agent Engineering 经验库，不再为单次事故建立交接、经验或完成报告。旧规则失效时直接更新当前规则，历史由 Git 保存，不让多份“当前约定”互相覆盖。

收口时交付已完成结果、仍需用户选择或验收的事项、具体报告／文档入口与本批 Commit ID；未能提交时说明具体阻碍并保留精确补丁与新增文件清单，不把安全备份称为发布包，不擅自推送。

## 10. 文档维护与新建门槛

文档维护坚持“已有职责优先、单一事实入口、Git 保存旧版本”。先判断已有哪份文档负责这类信息，再在原文档中合并、修正或替换；不要为了本轮工作看起来完整而增加小文档。

| 变化类型 | 唯一或优先更新位置 |
| --- | --- |
| 当前进度、普通 Bug、已知限制、最新验证结果 | `current_status.md` |
| 用户可见能力、推荐表达、确认与失败边界 | `capability_boundaries.md` |
| RoxyPlan 特有协作习惯、诊断和验证流程 | `project_workflow.md`；硬边界同时更新根 `AGENTS.md` |
| 可复用 Agent Engineering 经验、反证和认知修正 | `agent_engineering_experience.md` |
| Memory、状态、回复真实性、历史、成长、客户端动作等技术契约 | 对应的现有专题文档 |
| 未来方向 | `ROADMAP.md` |
| 已完成正式里程碑 | `CHANGELOG.md` |
| 明确存在但暂不处理的结构性问题 | `technical_debt_register.md` |
| 测试方法或 lane 规则 | `tests/README.md`；带日期结果仍只进 `current_status.md` |
| 外部开源或模型研究 | 只有研究会影响架构决策并需要长期复查时，才更新或新增 `research/` 材料 |
| 学习路径或文件职责 | 现有 `learning/` 文件，不建立第二套教程 |

新的项目经验不单独建文件：已有条目补充新证据和适用边界；真正的新原则在同一经验库增加新的 `E` 编号；推翻旧结论时在原条目记录旧判断、反证和替代结论。普通执行错误、一次测试数字和未验证推测不进入经验库。

默认禁止创建版本交接、事故经验、修复总结、完成报告、带版本号的设计副本以及普通开发产生的 `analysis/` 文档。只有同时满足“全新稳定领域、现有文档无法容纳、预计反复维护使用、职责边界清楚、用户明确批准”时，才新建长期文档。

# RoxyPlan 产品与可靠性原则

更新时间：2026-07-29

RoxyPlan 是长期成长陪伴桌宠。功能数量不是当前目标；真实可用、自然、可解释、可回退才是演进标准。

1. 用户体验优先于技术炫技。
2. 系统应主动理解不完整、不规范和口语化表达，不因措辞不标准频繁要求用户整句重说。
3. 本地规则只承担高精度、低歧义、长期稳定的命令、查询、否定和确认；不以完整句正则追赶所有中文。
4. 规则无法可靠覆盖的表达交给模型做结构化语义理解。
5. 模型只能提出请求模式、意图、参数候选和动作计划，不能直接执行工具，也不能决定真实业务对象 ID。
6. `BusinessResolver` 必须从本地真实数据查询、匹配并验证计划、记忆、候选和行动记录对象。
7. 普通聊天、讨论、建议、愿望、查询、执行、纠正、取消和确认必须区分。
8. 查询、普通聊天、建议及明确可逆低风险操作不应增加无意义确认。
9. 模糊写操作、高风险操作、不可逆操作、批量覆盖和多个候选对象必须分别进入澄清、选择或确认，不能用低置信度确认替代澄清。
10. 多步请求先展示整体动作预览，通常只确认一次；内部逐项执行，有依赖动作按序，独立动作采用 best effort。
11. 一个独立动作失败不能取消其他动作；每项结果分别记录、分别解释。
12. 所有成功、失败和“没有数据”的事实必须来自真实 `ToolResult`、`BatchToolResult` 或 `ClientActionResult`，回复不得脱离执行证据。
13. 助手可以指出用户方案的问题并给出替代建议，不机械迎合。
14. 关键改动必须经过真实桌面入口或真实业务组合根测试，Mock 和单元测试不能替代真实链验收。
15. 新功能必须先进入 `CapabilityRegistry`；工具 schema、风险和确认策略从统一目录取得，alias 只能映射到 canonical tool。
16. 新模块必须有唯一职责、明确调用者和旧职责退出计划，不能持续堆叠 Manager、Parser 或 Coordinator。
17. 不为指标修改测试答案、删除困难样例、降低标准或泄漏冻结集。
18. 所有准确率必须说明 CapabilityRegistry 闭集、数据来源、划分与限制，不宣称覆盖全部中文自然语言。
19. 本轮工作属于 evaluation、hardening、iterative improvement 和 benchmark-driven development，不属于模型训练或微调。
20. 私人记忆、计划、记录、历史和配置不得进入测试集；测试只使用临时目录和隔离数据。

## 变更门槛

每项可靠性改动至少回答：用户价值是什么、命中了哪个 Capability、是否写数据、风险等级、确认策略、证据来源、真实入口测试、回滚 flag。任何无法安全确定的写操作都应降级为精准澄清，而不是猜测执行。

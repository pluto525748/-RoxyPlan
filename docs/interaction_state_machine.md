# V2.2 交互状态机

更新时间：2026-10-15

`InteractionStateCoordinator` 管理对话操作状态，不管理桌宠动画状态。状态仅保存在当前进程内，并按 `conversation_id` 隔离。

## 状态

- `idle`：没有待处理交互。
- `candidates_listed`：已经列出真实业务对象，可以按编号或顺序选择。
- `awaiting_clarification`：缺少字段或目标不唯一。
- `awaiting_choice`：系统给出了建议或多个真实候选，等待用户选择。
- `awaiting_confirmation`：动作和不可变参数已经确定，等待确认或取消。
- `awaiting_tool_result`：已经进入安全工具执行。
- `partial_success / completed / cancelled / expired`：终态。

`确认`、`取消`、`第二个`、`就这个` 等控制表达优先交给协调器。有 pending 时普通模型不能重新解释整轮请求；同一个交互消费后不能重复执行。

明确今日全体完成（2026-10-15）：没有先前列表时，完整的“完成今天所有未完成计划”请求可先读取当日真实范围，建立稳定UID展示快照并进入原 `awaiting_confirmation`；本轮只展示、不完成。下一轮确认沿原执行器重新核验集合，目标变化或跨日即停止。模糊的“都完成了”等仍不能建立新的全体范围。今日建议快照保留完整长正文，继续验证整份容量、真实编号与用途，不能将方向或讲解列表绑定写入。

## 有效期与路由优先级

桌面端与 Local Web 使用同一组默认有效期：

- `awaiting_clarification`、`awaiting_choice`：20 分钟，给普通澄清和自然选择留出足够时间。
- `awaiting_confirmation`：3 分钟，与不可变工具参数的正式确认窗口保持一致。
- 其他短时 pending（候选列表、候选选择、工具结果等待）：5 分钟。

三个值分别由 `interaction_continuation_ttl_seconds`、`interaction_confirmation_ttl_seconds` 和 `interaction_ttl_seconds` 控制。旧调用方只传 `interaction_ttl_seconds` 时仍沿用单一有效期。交互切换到另一类 pending 状态时，按新状态类别重新计算截止时间；普通字段更新不会无限续期。

除确认/选择外，同一个有界操作最多给出两轮澄清。第二轮后仍缺少字段或唯一目标时，协调器取消该 pending，清除对应确认上下文，返回统一的“本次没有完成 + 可执行示例”，且不执行工具、不修改数据。新消息若已经是具体且不兼容的新请求，仍可按新话题规则取消旧 pending，而不是消耗澄清轮次。

当前会话存在兼容 pending 时，结构化 continuation 必须优先于“上一条助手回复”“刚才说的”等 fresh reference 路由。只有没有可消费的 pending 时，才允许从聊天历史解析 assistant plan reference。不兼容的新话题仍会取消旧 pending，再按新消息处理。

桌面端在当前聊天会话仍有 pending 时不会插入主动提醒，避免提醒消息改变“刚才”“这个”等指代的可见来源；pending 结束或过期后，提醒检查会自然恢复。

状态同时保存 `domain`、`request_mode`、原始请求、已知/缺失字段、建议选项、不可变参数和上一条用户事实。后续短句会先补入当前任务，例如“我下午想学一会儿”后的“特征工程，一个小时”会保留下午并补齐标题与时长；“不知道，你安排”会转为建议选择，不会直接写计划。若当前用户句明确出现“今天/昨天/明天”等日期，它优先于 pending、上一轮只读结果和模型返回的残留日期；只有当前句没有新日期时才允许沿用结构化上下文。

交互类型包括缺字段、建议选择、建议或执行选择、业务对象选择、行动记录建议、计划更新、重复计划处理、短期记忆去向、候选审核、危险工具和多动作审核。取消、超时或新会话会清除会话级引用，不影响真实业务数据。

## 学习开始的临时方式选择

2026-10-14 增加只读讨论选择 `discussion_choice`：复用已展示选项、原始请求与现有已知字段，在当前进程保存列表用途，不绑定工具参数。用途由原请求的多日范围、编号列表之外的澄清说明、阶段标题及既有带学模式共同核验；语义 advice 标记和编号格式本身不授权写入。目标短答只交给原普通聊天路径继续讨论，不增加一次列表分类模型请求，也不自动保存记忆或行动。未知或不可唯一匹配的回答按新话题／取消规则处理。

建立讨论列表时清除旧的可采用今日建议快照；只有今日任务用途的快照可进入原采用链。单项单日行动须另有明确新增请求，随后仍使用原日期、参数、工具与后置条件校验；周阶段、方向选项、整批长期方案不能从只读选择升级成今日写入。列表用途判断是本地有限校验，本批离线通过不代表在线模型任意表达已验收。

2026-10-13 增加 `learning_mode_choice`，只在现有进程内保存本次学习主题。`advice_or_action_choice` 中的“开始／现在开始”先进入该选择，不取消原主题重新猜写入意图；“先听建议”与明确加入计划仍沿原分支。选择带学后结束该 pending，使用普通聊天模型讲解具体第一步，且不建立可写计划的建议快照；自主学习只提示完成后回面板勾选。取消、超时或新话题沿用现有清理，无新业务存储和计时。

## ReadSnapshot、展示顺序与实时复核

成功 `show_plan` 后，协调器在当前 `conversation_id` 保存结构化 `ReadSnapshot`，包括 `snapshot_id`、工具与查询参数、每个对象的稳定 ID、`display_order` 以及有限的标题、日期、状态和时长字段。快照按 continuation TTL 失效，不跨会话，也不是一份新的业务数据副本。

后续“第二项完成了”按快照中的 `display_order` 找到当时展示对象的稳定 ID，而不是用已经变化的实时列表下标重新解释。执行前再从计划服务按该稳定 ID 读取现状；对象不存在、日期不受支持或不可用时诚实终结，不得改到其他对象。对象已完成时说明无需重复，零工具、零写入；已完成／已删除的计划不能转成计划外行动提议，也不能转入新增计划流程。

“第二项我做完了，其余先不动”“第一项别动，第二项完成”等表达中的排除子句只限制范围；有唯一明确肯定序号且快照仍有效时，仅按该序号的稳定 ID 完成单项。“其余／其他”本身不将这类请求升级为批量。以真实完整标题明确完成单项时同样适用：语义已选择完成能力后，“其余先不动”等完整排除子句不参与肯定批量范围判断；原始输入仍交给对象、日期与授权校验，不因这层范围投影取得新的写入许可。快照过期、跨日或对象变化时零写入；真正集合完成继续走下述预览和统一确认。

当前句明确出现真实完整计划标题时，该标题优先于其内部的序号/数量词。例如“完成计划：读一个章节”不能因“一个”而完成展示第一项，“阅读第二个小节”也不能改到展示第二项。模型已选择完成能力后，引用层只校正真实对象身份；数量不是列表索引，重复同标题仍交由现有对象解析处理，不猜选一条。

引用层绑定后以本地 `read_snapshot_binding` 来源传给 BusinessResolver（不是工具参数，也不是模型提供的字段）；可靠当前句实体校正使用 `current_sentence_binding`。业务解析器继续按稳定 ID 核验真实状态，但不能再按当前列表顺序或标题内“第二个”重新解析该对象；目标后来完成或删除时也保留绑定来源，不允许失败后落到另一条实时序号。精确标题的状态判断先于待完成项的模糊匹配，不能因为精确对象已完成而转到相似未完成项。

“刚才展示的计划我都完成了”等批量完成先按快照稳定 ID 复核当前仍可完成的对象，列出一次预览并进入 `plan_batch_completion`。预览阶段零写入，用户回复“确认”或“对”后只执行已预览的完整目标集合；确认前会再次读取已选稳定 ID，集合失效时整批不执行并要求重新查看计划。没有可核验集合的批量表达，以及没有真实待确认操作时的简短附和，都不得由模型缩成单项完成。这个批量完成契约不受模型自由多动作最多三项的上限影响。

“全部／剩下的”等集合控制只消费语义链已选能力或当前同类型 pending 的真实范围，不作为普通聊天升级写操作的规则。疑问、数量不符、旧日期、过期或跨会话范围不能写入；集合中有删除成员时停止，不偷偷缩小范围。全部已完成则诚实说明无需重复；无法继续的失败同时清除协调器与 ConfirmationManager 的 pending。

## SuggestionSnapshot 与连续添加

建议列表使用独立的 `SuggestionSnapshot`：会话、来源轮次、有限期、建议项稳定 ID、展示顺序、标题和 consumed 状态。它不是今日计划的 `ReadSnapshot`，也不是第二份业务 pending 数据；当前类型化交互只引用这份快照，第一项执行结束后仍可引用同一真实建议列表的未处理项。

建议快照保留原请求的共同日期、时段约束，采用时复用用户实际看到的候选，不再调用模型重释建议。候选正文可可靠拆分时分别保存简洁标题、完整说明备注和时长；本轮明确修改的时段覆盖原约束。2026-10-11 起，明确的今日计划建议还在聊天历史元数据中记录生成时的业务日期、会话／请求关联、简要事实与覆盖范围、实际展示候选及采用后的最终计划 UID；可靠对应昨日未完成任务时，快照候选保留其来源 UID／日期，不自动移动或修改昨日任务。历史保存失败会明确说明证据未留存。计划外行动进入待确认时，提示从 pending 的不可变参数展示具体内容与已知时长，缺时长写“时长未记录”；切换待确认对象后同步更新提示。

模型首次给出合法计划候选后，交互进入 `assistant_plan_offer`。用户可以直接选择一项或要求全部加入；这条路径不经过额外澄清。若用户只补充一个方向、时间或风格条件，则先进入 `assistant_plan_refinement`，把原始请求与本轮补充交给模型重新生成候选；该阶段不调用工具、不写计划。通过结构校验的新列表进入 `assistant_plan_selection`，同一 offer 最多接受一次这种细化，防止模型连续追问和状态无限延长。

一次细化后再收到短句调整条件时，不让它回落到普通语义写入，也不让模型继续显示新列表却沿用旧快照。协调器取消本轮并清除建议快照，回复一次调整限制与完整重新请求的示例；用户可以重新请求新建议，新请求重新建立自己的快照。第二次短句调整以及随后对旧列表说“全部加入”都必须零工具、零写入。这个“一次细化”限制与一般缺字段交互的两轮澄清上限是不同边界。

2026-10-07 起，可核验的助手单层编号清单以用户实际看到的完整内容为准；用户后续明确引用它时，不再让模型第二次提取并截成前三项。清单项数不预设为二、三或四；“就按这几条安排”等有有效 pending 的整批表达按完整未消费范围处理，显式数量不符则零写入。简短的“好”不作为细化条件；只有实际补充学习方向、事项、时间或数量等条件才重新生成建议。标题中出现“这些标记”等词，不等于整项没有具体内容；只有整个标题仍是“这些／刚才那些安排”等泛指时才拦截。普通聊天偶然编号、跨会话和过期列表仍不得凭空建立执行权限。

是否在候选列表后自然邀请用户补充，由模型根据当前信息是否充分决定；本地程序不追加固定引导句。系统提示只要求：信息充分时直接给可用建议，确有价值时可以自然说明“可直接选择，也可补充一次”，不得把补充当成执行条件。无论模型是否写出这句提示，本地 offer 都同时支持直接执行和一次可选细化。

用户对有效建议快照说“全部加入今日计划”时，系统先核验完整未处理集合，再在同一轮逐项调用现有新增计划工具，不受模型自由多动作三项上限约束。发现重复项时，任何新项都暂不写入，进入 `suggestion_batch_duplicate_resolution`，只统一等待“添加未重复项／仍然全部添加／取消”之一；疑问、否定、快照变化或无法核验时零写入退出。

给出可加入计划的多项学习建议时，提示模型使用与程序兼容的单层编号列表，一项一个具体行动。受限提取结果必须能在真实助手原回复中核验；本地可靠学习方向列表使用同一快照结构。没有可核验列表时不编造事项。

“第二个也加入”先由语义链选择计划候选，本地随后只校正引用实体。普通新项仍使用 `add_plan`，并将确切标题和当前句明确的日期、时段、时长送入已有结构校验；建议承接今日已有未完成项时，仅“原计划完整标题：更小动作”且唯一对应才改走 `update_plan`，保留原稳定 ID。snapshot ID 和建议项 ID 只作为内部操作来源，不进入工具参数；普通新增的 `task_ref` 等非法参数不会泄漏到执行器。“再加一条”“一个小时”等数量表达不属于序号，当前句真实标题及已可靠解析的 typed continuation 也不能被这层绑定覆盖。

只有成功 `add_plan` 或已核验原 ID 与新标题的 `update_plan` ToolResult 才消费选中的单项。无法唯一对应今天的原任务时零写入并请用户明确原计划完整标题；只有明确“另建一项／拆成两项”才保留原项并新增。几周前的过期任务仅与新标题共享主题词，不构成修改今天任务的证据。混合今天旧任务承接项的“全部加入”整批零写入，要求逐项选择，不能把承接项静默变成新项。重复计划确认、分轮补齐必要字段时保留来源，取消、失败不消费；超时、跨会话、越界或已消费项目均不得猜测写入。普通新增仍只要求标题，不增加强制时长，也不放宽两轮澄清上限。

“全部都加入／剩下的都加入”沿同一新增语义链选取当前快照的完整未消费集合，不受模型自由生成多动作最多三项的上限约束；显式数量必须与范围一致，不截断列表。消费依据各项真实成功结果与已添加标题逐项匹配，同标题多项不能因为一条成功就一起被标为已消费。空集合、失效集合和无法核验的结果保留诚实退出，不凭模型摘要消费。

## 真实确认与回复投影

已完整解析的明确多项新增计划由本地计划授权准许时直接走原批量执行，模型单独给出的确认提示不增加一次确认。若本地授权仍要求确认，多项 `add_plan` 保存在同一个 `plan_batch_addition` 待确认状态，提示逐项列出完整范围；确认前核对绑定的业务日期和全部待添加项，确认后一次性交给原批量执行器。取消、过期、跨日、确认前对象变化和重复确认不会把第二项遗漏或重复添加；部分工具执行失败仍按各项实际 ToolResult 报告，不声称整批成功。

显式、肯定的唯一单项删除可沿既有本地绑定路径建立一次真实确认，当前句明确真实标题／ID优先于旧模型引用；未开放的集合删除不缩成单项，无法绑定不建立纯文本假确认。确认前仍核验不可变目标，提前退出保留脱敏语义 diagnostics。

`VerifiedTurnContext` 的 `confirmation_pending` 只由当前真实、合法的待确认操作生成，向回复模型提供脱敏的能力与目标数量，不提供正文、目标 ID 或参数。状态名称、助手上一句承诺或无关写工具成功都不足以证明存在这项操作；投影只说明待确认，不能证明已执行。字段形状与合法能力仍以运行代码和注册表为准，本文不复制另一份 schema。

## 重复计划、隐藏复杂能力与记忆确认

`duplicate_plan_resolution` 保存已查询到的真实候选 ID、待添加参数和只读合并预览。它是本地确定性/兼容路径的有界状态，不表示修改、合并、改期、删除等复杂工具对模型开放。进入受支持路径后，用户可以更新原计划、仍然添加、合并或取消；合并遇到时段、时长、优先级或备注冲突时保持该状态并逐项询问，冲突消解后进入常规 `awaiting_confirmation`，确认前不改数据。

`memory_or_plan_destination` 只处理当前消息中同时出现“记住”和当天时间范围的歧义。它保存两份受限参数：今日计划参数与长期记忆参数。用户选择后只提交对应的一种工具，不会同时写入两个系统，也不会把该选择扩展成开放文本意图规则。

普通、稳定且非敏感的信息在用户没有明确要求保存时，只能进入当前进程的 `formal_memory_save` 确认状态。确认前不创建磁盘候选、不写 `memory.json`、不产生成功 ToolResult；取消、超时或澄清耗尽会直接清除 pending。健康等敏感信息在没有明确保存命令时不主动建议保存，也不建立该 pending。显式且内容完整的“记住……”仍沿既有正式记忆工具契约处理。

`CapabilityRegistry` 是模型可见性和副作用、风险、确认策略、可逆性等执行策略的唯一权威；`ToolRegistry` 只提供参数 schema、别名与 handler。默认隐藏的复杂修改、合并和候选/记忆维护工具即使被模型提议，也不能进入执行状态，而应以零工具、零写入的统一诚实降级结束。

## 标识边界

- `user_id`：本地用户范围，长期数据归属。
- `conversation_id`：会话边界；引用和 pending 不跨会话。
- `interaction_id`：一次澄清或确认过程。
- `tool_call_id`：一次实际工具调用。
- `resource_id`：计划、记忆或候选的真实本地标识。

新会话只清除会话引用与 pending，不删除长期记忆、候选、计划或成长数据。进程重启后危险确认失效，候选数据本身仍保留。

## 回滚

配置 `interaction_coordinator_enabled=false` 可回到旧会话控制路径，不需要迁移数据。诊断功能由 `interaction_diagnostics_enabled` 单独控制，默认关闭。

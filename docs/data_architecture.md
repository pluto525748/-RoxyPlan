# RoxyPlan 数据存储方案

## 1. 设计目标

RoxyPlan 的核心目标是帮助用户持续成长，而不是单纯聊天。

因此数据存储方案必须服务于：

- 学习记录。
- 健康记录。
- 项目进度。
- 赚钱记录。
- 长期成长。
- 长期记忆。
- 知识库查询。
- 对话上下文。

核心原则：

- 结构化数据优先进入 SQLite。
- 长期人格化记忆保存在 本地长期记忆文件。
- 知识库独立于长期记忆。
- 聊天记录独立于长期记忆。
- 成长日志独立于聊天记录。
- 用户可查看、可编辑、可删除关键数据。
- 敏感数据要谨慎存储。

## 2. 存储分层

RoxyPlan 建议采用以下存储分层：

```text
data/
├─ roxyplan.sqlite
├─ 本地长期记忆文件
├─ knowledge_base/
├─ chat_history/
└─ growth_log/
```

说明：

- `roxyplan.sqlite`：主要结构化数据存储。
- 本地长期记忆文件：长期记忆和人格化用户档案。
- `knowledge_base/`：知识库文件、解析结果、索引和引用信息。
- `chat_history/`：聊天记录导出、备份或归档。
- `growth_log/`：成长日志导出、周报月报归档或备份。

## 3. SQLite

### 3.1 定位

SQLite 是 RoxyPlan 的主数据存储。

适合保存：

- 需要查询的数据。
- 需要排序的数据。
- 需要筛选的数据。
- 需要关联的数据。
- 需要统计的数据。
- 需要分页展示的数据。

### 3.2 应放入 SQLite 的数据

聊天相关：

- 会话列表。
- 消息记录。
- 消息角色。
- 消息时间。
- 消息状态。
- 消息关联的记忆或知识引用。

成长相关：

- 学习记录。
- 项目进度。
- 健身记录。
- 收入记录。
- 心情记录。
- 今日计划。
- 周报。
- 月报。

知识库相关：

- 文件记录。
- 文件解析状态。
- 知识块元数据。
- 知识标签。
- 引用信息。
- 检索索引元数据。

系统相关：

- 用户设置。
- 桌宠设置。
- 语音设置。
- 同步状态。
- 通知状态。

### 3.3 不建议放入 SQLite 的数据

不建议直接放入 SQLite 的内容：

- 大型原始文件。
- 大段解析全文。
- 大型向量文件。
- 用户明确希望便于手动编辑的长期记忆。
- 可独立备份的知识库文件。

这些内容更适合放在 JSON 文件、文本文件或知识库目录中，再由 SQLite 保存索引和元数据。

### 3.4 SQLite 的优势

- 查询方便。
- 适合成长记录统计。
- 适合聊天历史分页。
- 适合按时间生成周报和月报。
- 适合管理知识库文件状态。
- 适合桌面端和手机端同步。

### 3.5 SQLite 的边界

SQLite 不应承担所有事情。

它不应该变成：

- 大文件仓库。
- 长期记忆唯一来源。
- 知识库全文唯一存储。
- 复杂 AI 推理状态存储。

## 4. 本地长期记忆文件

### 4.1 定位

本地长期记忆文件 是 Roxy 的长期记忆文件。

它保存的是对 Roxy 人格化陪伴有长期价值的信息，而不是普通聊天记录。

### 4.2 应放入 本地长期记忆文件 的数据

适合放入 本地长期记忆文件：

- 用户档案。
- 用户称呼。
- 沟通偏好。
- 长期目标摘要。
- 重要项目摘要。
- 学习偏好。
- 健康提醒偏好。
- 兴趣爱好。
- Roxy 成长阶段。
- 用户明确要求记住的内容。
- 记忆设置。
- 记忆审计摘要。

### 4.3 不应放入 本地长期记忆文件 的数据

不应放入 本地长期记忆文件：

- 完整聊天记录。
- 每日所有成长记录。
- 大量知识库全文。
- 原始上传文件。
- 大量收入流水。
- 未确认的敏感健康信息。
- 密码、密钥、验证码。

### 4.4 为什么长期记忆放 JSON

原因：

- 易于查看。
- 易于备份。
- 易于手动编辑。
- 适合作为 Roxy 的人格记忆快照。
- 不依赖复杂数据库查询。

本地长期记忆文件 应保持小而精，不追求记录所有内容。

### 4.5 本地长期记忆文件 与 SQLite 的关系

本地长期记忆文件保存长期记忆摘要。
SQLite 保存可查询的详细记录。

示例：

- SQLite 保存每天的学习记录。
- 本地长期记忆文件 保存“用户正在长期学习 Python，并偏好用项目驱动学习”。

- SQLite 保存项目进度流水。
- 本地长期记忆文件 保存“RoxyPlan 是用户当前重要项目之一，目标是做长期成长陪伴 AI 桌宠”。

## 5. knowledge_base

### 5.1 定位

`knowledge_base` 是用户投喂资料的存储区域。

它和长期记忆不同：

- 知识库保存资料内容。
- 长期记忆保存关于用户的稳定信息。

### 5.2 建议目录结构

```text
data/knowledge_base/
├─ files/
├─ parsed/
├─ chunks/
├─ indexes/
└─ exports/
```

说明：

- `files/`：原始投喂文件。
- `parsed/`：解析后的文本和结构。
- `chunks/`：知识块内容。
- `indexes/`：检索索引、向量索引或全文索引。
- `exports/`：知识库导出备份。

### 5.3 应放入 knowledge_base 的数据

适合放入：

- PDF 原始文件。
- Word 原始文件。
- PPT 原始文件。
- TXT 原始文件。
- Markdown 原始文件。
- 解析后的文本。
- 文档结构。
- 知识块正文。
- 向量索引文件。
- 知识库导出文件。

### 5.4 应放入 SQLite 的知识库数据

知识库中应进入 SQLite 的部分：

- 文件 ID。
- 文件名。
- 文件类型。
- 文件大小。
- 解析状态。
- 上传时间。
- 标签。
- 项目绑定。
- 知识块 ID。
- 知识块摘要。
- 引用位置。
- 是否启用。

### 5.5 不应放入 本地长期记忆文件 的知识库数据

不应把投喂资料全文放入 本地长期记忆文件。

只有当用户明确说“这个项目是我的长期目标，请记住”时，才把资料相关摘要写入长期记忆。

## 6. chat_history

### 6.1 定位

`chat_history` 保存对话记录。

主存储应放在 SQLite。  
`chat_history/` 目录可用于导出、备份和归档。

### 6.2 SQLite 中的聊天数据

应进入 SQLite：

- 会话 ID。
- 消息 ID。
- 消息角色。
- 消息内容。
- 消息时间。
- 消息类型。
- 是否引用知识库。
- 是否触发记忆确认。
- 是否关联成长记录。

### 6.3 chat_history 目录中的数据

适合放入 `chat_history/`：

- 按日期导出的聊天记录。
- 按项目导出的聊天记录。
- 用户手动备份。
- 调试或迁移用归档。

### 6.4 聊天记录与长期记忆的区别

聊天记录是发生过的对话。  
长期记忆是经过筛选、确认、有长期价值的信息。

示例：

- 用户说：“今天我有点累。”  
  这是聊天记录，不一定是长期记忆。

- 用户说：“以后我希望你提醒我每晚 11 点前睡觉，请记住。”  
  这可以进入长期记忆。

## 7. growth_log

### 7.1 定位

`growth_log` 保存用户从 22 岁到毕业的成长过程。

主存储应放在 SQLite。  
`growth_log/` 目录可用于导出、报告归档和备份。

### 7.2 SQLite 中的成长数据

应进入 SQLite：

- 今日计划。
- 学习记录。
- 项目进度。
- 健身记录。
- 收入记录。
- 心情记录。
- 周报。
- 月报。
- 目标关联。
- 项目关联。

原因：

- 这些数据需要按日期查询。
- 需要生成趋势。
- 需要筛选分类。
- 需要周报月报统计。

### 7.3 growth_log 目录中的数据

适合放入 `growth_log/`：

- 周报导出。
- 月报导出。
- 毕业阶段总结。
- 用户手动备份。
- 成长记录快照。

### 7.4 成长记录与长期记忆的区别

成长记录保存具体发生的事情。  
长期记忆保存稳定结论和长期偏好。

示例：

- SQLite 保存：“2026-06-05 学习 Python 60 分钟。”
- 本地长期记忆文件 保存：“用户正在长期学习 Python，偏好项目驱动方式。”

- SQLite 保存：“本月项目收入 500 元。”
- 本地长期记忆文件 不保存具体收入流水，只可能保存“用户正在尝试通过项目赚钱”这类用户确认过的长期目标。

## 8. 什么数据放数据库

建议放 SQLite 的数据：

### 8.1 高频变化数据

- 聊天消息。
- 今日计划。
- 学习记录。
- 项目进度。
- 健身记录。
- 收入记录。
- 心情记录。
- 通知状态。

原因：

- 高频新增。
- 需要排序。
- 需要分页。
- 需要统计。

### 8.2 可查询数据

- 历史会话。
- 成长日志。
- 知识文件列表。
- 知识块元数据。
- 标签。
- 周报月报。

原因：

- 需要搜索。
- 需要过滤。
- 需要按时间查询。
- 需要关联项目和目标。

### 8.3 关联数据

- 记录与目标的关系。
- 项目与知识文件的关系。
- 聊天与知识引用的关系。
- 记忆与来源聊天的关系。

原因：

- 关系查询更适合数据库。
- 后续同步和移动端访问更清楚。

## 9. 什么数据放 JSON

建议放 JSON 的数据：

### 9.1 长期记忆快照

- 用户档案。
- 长期目标摘要。
- 沟通偏好。
- 兴趣爱好。
- Roxy 成长阶段。
- 记忆设置。

原因：

- 低频变化。
- 需要用户可读。
- 需要容易备份。
- 适合作为人格记忆上下文。

### 9.2 配置类数据

可放 JSON 或 SQLite，取决于复杂度。

适合 JSON：

- 简单桌宠设置。
- 简单语音设置。
- 本地 UI 偏好。

适合 SQLite：

- 需要跨端同步的设置。
- 需要审计的设置。
- 需要按设备区分的设置。

### 9.3 导出和快照

适合 JSON：

- 成长日志导出。
- 记忆备份。
- 周报月报快照。
- 知识库摘要导出。

这些可以作为备份，不一定是主存储。

## 10. 推荐最终分配

### 10.1 SQLite

放：

- 聊天记录主数据。
- 成长日志主数据。
- 今日计划。
- 周报月报。
- 知识库元数据。
- 文件解析状态。
- 标签和关联关系。
- 设置和同步状态。

### 10.2 本地长期记忆文件

放：

- 用户档案。
- 长期目标摘要。
- 稳定偏好。
- 重要项目摘要。
- 兴趣爱好。
- Roxy 成长状态。
- 记忆设置。

### 10.3 knowledge_base

放：

- 原始投喂文件。
- 解析文本。
- 知识块正文。
- 检索索引文件。
- 知识库导出。

### 10.4 chat_history

放：

- 聊天记录导出。
- 会话备份。

主聊天数据仍在 SQLite。

### 10.5 growth_log

放：

- 周报导出。
- 月报导出。
- 毕业成长总结。
- 成长数据备份。

主成长日志数据仍在 SQLite。

## 11. 隐私设计

敏感数据包括：

- 收入记录。
- 健康记录。
- 心情记录。
- 长期记忆。
- 用户档案。
- 私密项目。

规则：

- 敏感数据默认本地优先。
- 用户可以删除。
- 跨端同步需要明确开启。
- 手机端展示敏感数据时应谨慎。
- 不把敏感聊天内容自动写入长期记忆。

## 12. 与手机版同步的关系

手机版通过同步服务访问轻量数据。

优先同步：

- 今日计划。
- 最近聊天。
- 成长记录摘要。
- 长期记忆摘要。
- 知识库查询结果。

不优先同步：

- 大型原始文件。
- 完整解析文本。
- 大型索引文件。

桌面端仍是主要数据中心。  
手机端是轻量访问和记录入口。

## 总结

RoxyPlan 的数据存储应采用“SQLite 主结构化数据 + 本地长期记忆文件 长期记忆 + knowledge_base 知识库文件 + 导出目录”的组合。

最重要的边界是：

- 数据库保存可查询、可统计、可关联的事实记录。
- JSON 保存低频变化、用户可读、人格化的长期记忆。
- 知识库保存用户投喂资料和检索内容。
- 聊天记录不等于长期记忆。
- 成长日志不等于聊天记录。

这样 RoxyPlan 才能既保持长期成长系统的结构清晰，又保留用户对记忆和隐私的控制感。
